Services

For apps built on Supabase

Supabase security audits

Can a signed-in user read or change someone else’s rows? A scanner tells you whether row-level security is on. I prove whether it holds, for every table and every role, and you keep the tests.

What you get

Yours to keep

  1. An access matrix

    Who can read, add, change and delete what, table by table and role by role: what you meant, then what the database does.

  2. A test suite you can replay

    pgTAP tests that run with supabase test db, after every migration, long after the audit.

  3. Findings ranked by severity

    Each one with the exact query that proves it, and what it takes to close it.

  4. Fixes, if you want them

    An additive migration and a pull request, then the tests run again.

Method

No production data

  1. From your schema

    Your migrations, on a local copy of the database, with made-up users: anonymous, user A, user B, admin. Your users’ data never leaves your project.

  2. A written authorization first

    Nothing is queried before it is signed. I never touch a production database.

  3. What is not covered, written down

    The report lists what the tests do not reach, so that nothing reads as checked when it was not.
